# auto-6ce31094
## Diagnosis
The `forbidden-generic-api` contract fires in `method-check` even after `autoRepairForbiddenGenericApis` runs because the two regular expressions are not equivalent. The repair regex `\(\s*\)` only matches truly empty argument lists (whitespace only), while the detection regex `\(` matches any open-paren that follows `<Type>`. When AI-generated code has a `.GetComponent<T>()` call where the parens contain anything other than pure whitespace — for example an inline `/* comment */`, a stray argument, or a newline — the repair silently skips it, the detection still fires, and the stage rejects the code despite the auto-repair guard running first.

## Root Cause
`engine/stages/method-check.cjs` : line 255 — `stripGenericGetComponentCalls` uses `/\.GetComponent\s*<\s*([A-Za-z_][A-Za-z0-9_.]*)\s*>\s*\(\s*\)/g` (strict `\(\s*\)` empty-arg group), while `detectForbiddenGenericApis` at line 588 uses `/\.GetComponent\s*<\s*([A-Za-z_][A-Za-z0-9_.]*)\s*>\s*\(/g` (bare open-paren, no closing-paren requirement). This asymmetry means the repair can miss patterns the detection catches.

## Fix
In `engine/stages/method-check.cjs`, change the `stripGenericGetComponentCalls` function body (lines 251–259) so the replacement regex uses `[^)]*` instead of `\s*` between the parentheses — this captures any argument content that does not contain a nested closing paren, making it a strict superset of what the detection regex matches:
